## ЛР №3. Docker + Nginx + Gzip

### Что сделал

- Включил в Unity сжатие WebGL в Gzip и выключил Decompression Fallback.
- Собрал игру через `BuildManager.BuildWebGL`, получил файлы `WebGL.framework.js.gz`, `WebGL.wasm.gz`, `WebGL.data.gz`.
- Написал `nginx.conf`, который добавляет заголовок `Content-Encoding: gzip`.
- Написал `Dockerfile` на базе `nginx:alpine`, который кладёт игру и конфиг внутрь образа.
- Собрал образ, запустил контейнер на порту 8080, проверил заголовок.
- Добавил в пайплайн задачу `build_docker_image`, которая собирает образ и публикует его в GHCR.

### Вопрос 1. Какую проблему решает `add_header Content-Encoding gzip;`?

Файл `.wasm.gz` — это сжатый файл. Сам по себе он выглядит для браузера как непонятный набор байтов. Заголовок `Content-Encoding: gzip` говорит браузеру: «внутри gzip, сначала распакуй, потом запускай». Без него браузер пытается выполнить сжатые данные как код и падает с ошибкой «Unable to parse».

### Вопрос 2. Зачем в пайплайне создавать пустые файлы через `touch`?

Папка `Builds/WebGL` исключена из Git через `.gitignore` — там лежат результаты сборки, их не хранят в репозитории. На облачном сервере этой папки нет, а Dockerfile делает `COPY Builds/WebGL/`. Если папки нет, `docker build` упадёт. Поэтому пайплайн создаёт пустые заглушки `.gz`, чтобы проверить сам механизм сборки образа. В ЛР №5 заглушки заменяются настоящей игрой.

### Вопрос 3. Куда внутри контейнера копировать файлы игры?

В `/usr/share/nginx/html/` — это стандартная папка статики у образа `nginx:alpine`. Именно её Nginx раздаёт по порту 80. В `nginx.conf` там указан `root /usr/share/nginx/html`.

### Вопрос 4. Зачем два тега — `latest` и `github.sha`?

`latest` — чтобы быстро запустить последнюю версию: `docker run ...:latest`. Тег с SHA коммита — чтобы точно знать, из какого кода собран образ, и откатиться на старую версию. Это как «последняя версия» и «версия с номером».

### Если спросят «что такое Docker?»

Docker — это упаковка приложения вместе с его окружением. `Dockerfile` — инструкция, как собрать образ. Образ — «чертёж» или «коробка» с программой. Контейнер — запущенная коробка. Плюс: на любом компьютере с Docker игра запускается одной командой, не нужно вручную ставить Nginx.

## ЛР №4. Тесты Unity в CI

### Что сделал

- Разделил код на сборки через `.asmdef`: игровая `GameAssembly`, тестовая `Tests` (только Editor) и `PlayModeTests`.
- Написал EditMode-тест: проверяет, что на сцене есть объект `Player`, у него тег `Player` и компоненты `PlayerController` и `Health`.
- Написал PlayMode-тест: проверяет, что здоровье уменьшается и персонаж умирает после трёх ударов.
- Написал тест по варианту 18: после смерти игрок появляется в точке спавна.
- Добавил в пайплайн задачу `run_tests`, которая запускает тесты в контейнере Unity.
- Сделал `build_docker_image` и `mirror_repo` зависимыми от тестов.
- Сломал тест специально, показал, что пайплайн красный, и вернул обратно.

### Вопрос 1. Чем EditMode отличается от PlayMode?

EditMode — тесты в редакторе без запуска игры. Быстро проверяют сцену, объекты, компоненты, настройки. PlayMode — тесты с запуском игрового цикла: работают `Awake`, `Update`, физика, корутины. Ими проверяют поведение: урон, смерть, возрождение.

### Вопрос 2. Зачем `.asmdef`?

`.asmdef` — это «отдельная полка» для кода. Игровые скрипты лежат на одной полке (`GameAssembly`), тесты — на другой. Тесты могут ссылаться на игровую полку и видеть классы, но сама тестовая полка не попадает в сборку игры. Плюс настройка `includePlatforms` говорит Unity, в каком режиме запускать тесты: `Editor` — только EditMode, без неё — PlayMode.

### Вопрос 3. Почему `build_docker_image` зависит от `run_tests`?

`needs: run_tests` — это очередь и фильтр. Пока тесты не прошли, Docker-образ не собирается. Если тест упал, задача сборки не запускается вообще (в GitHub Actions она будет `Skipped`). Так в GHCR не попадёт образ со сломанной игрой.

### Вопрос 4. Как `includePlatforms` влияет на режим тестов?

Если в тестовой сборке указано `"includePlatforms": ["Editor"]`, она существует только в редакторе, значит тесты EditMode. Если ограничения нет, сборка компилируется и для игры, значит тесты PlayMode. Поэтому тесты кладут в разные папки с разными `.asmdef`.

### Про вариант 18 — как рассказать

«Мой вариант — `PlayerSpawn` + `SpawnPoint`, PlayMode. Тест загружает настоящую сцену `SampleScene`, находит `GameController` и его модель. Запоминает позицию точки спавна. Телепортирует игрока на 8 метров в сторону, чтобы он точно был не на месте. Планирует событие `PlayerDeath`. Через 2 секунды `PlayerDeath` планирует `PlayerSpawn`, а `PlayerSpawn` телепортирует игрока в `model.spawnPoint` и возвращает здоровье. Тест ждёт 2,5 секунды и проверяет, что расстояние до точки спавна меньше 1 метра. Допуск 1 метр, потому что после телепорта игрок немного смещается физикой».

Если спросят «почему не 0?» — «потому что после телепорта проходит полсекунды, игрок успевает немного упасть/сдвинуться; 0,7 метра — это всё ещё точка спавна, а не старое место».

## ЛР №5. Облачная сборка WebGL и GitHub Pages

### Что сделал

- Включил Gzip и **Decompression Fallback** — для GitHub Pages.
- Добавил задачу `build_game`: она запускает `BuildManager.BuildWebGL` в контейнере Unity в облаке.
- Сборка загружается в артефакт `WebGL-Build`.
- `build_docker_image` скачивает этот артефакт и собирает образ с настоящей игрой.
- `deploy_to_pages` скачивает артефакт и публикует его в ветку `gh-pages`.
- В настройках репозитория включил GitHub Pages: ветка `gh-pages`, папка `/`.
- Игра открывается по адресу `https://tiasssd.github.io/2d_platformer/`.

### Вопрос 1. Почему `Builds/WebGL` в `.gitignore` и как файлы попадают в другие задачи?

`Builds/WebGL` — результат сборки, а не исходники. Это большие бинарные файлы, которые меняются при каждой сборке; в Git их хранить нельзя. Между задачами они передаются через артефакт: `build_game` делает `upload-artifact`, а `build_docker_image` и `deploy_to_pages` делают `download-artifact` в папку `Builds/WebGL`.

### Вопрос 2. Зачем `build_game` нужен `needs: run_tests`?

Чтобы не собирать игру из сломанного кода. Если тесты упали, `build_game` не запускается, а вместе с ней не запускаются Docker и Pages. Это экономит время и не публикует брак.

### Вопрос 3. Что делает `BuildManager.BuildWebGL` и почему пайплайн видит результат?

Метод берёт активные сцены из `EditorBuildSettings`, настраивает `BuildPlayerOptions` под WebGL и вызывает `BuildPipeline.BuildPlayer`. В конце смотрит `BuildSummary`: если успех — пишет `[CI/CD] УСПЕХ!`, если ошибка — пишет ошибку и завершает Unity с ненулевым кодом. Пайплайн видит код возврата и лог, поэтому понимает, собралось или нет.

### Вопрос 4. Почему Pages нужен Decompression Fallback, а Docker нет?

GitHub Pages — обычный статический хостинг. Он не умеет добавлять заголовок `Content-Encoding: gzip`. Поэтому Unity встраивает в сборку JavaScript-распаковщик, который распаковывает сжатые файлы прямо в браузере. В Docker стоит Nginx с нашим `nginx.conf`, который сам добавляет этот заголовок, поэтому там распаковщик не нужен.

**Важно про имена файлов:** при включённом Decompression Fallback Unity 6 переименовывает сжатые файлы в `.unityweb` (например, `WebGL.wasm.unityweb`). Внутри это тот же gzip (первые байты `1F 8B`), просто с другим расширением. JS-загрузчик видит `.unityweb` и распаковывает сам. Если fallback выключен, файлы называются `.gz`. Это взаимоисключающие режимы: либо `.gz` + заголовок от сервера, либо `.unityweb` + JS-распаковка. Для GitHub Pages нужен второй вариант.

### Вопрос 5. Чем отличаются Pages и Docker-образ?

GitHub Pages — бесплатный хостинг, ссылка открывается в браузере, но там только статические файлы. Docker-образ — переносимый артефакт: его можно запустить на любом сервере с Docker, внутри уже есть Nginx и игра. `latest` — последняя версия, `github.sha` — версия, привязанная к конкретному коммиту, для отката.

### Вопрос 6. Почему сайт может отдавать 404, если `deploy_to_pages` зелёный?

Потому что задача только публикует файлы в ветку `gh-pages`, но не включает сам хостинг. Нужно один раз зайти в `Settings → Pages`, выбрать `Deploy from a branch`, ветку `gh-pages` и папку `/`. После этого сайт заработает, а следующие сборки будут обновлять его автоматически.

### Если спросят про `game-ci/unity-builder` и почему CLI

«В методичке используется `game-ci/unity-builder@v4`, но он требует файл лицензии `.ulf` или серийный номер. Для бесплатной Unity Personal офлайн-лицензию больше не выдают, поэтому я использовал официальный CLI GameCI `game-ci build`, который умеет активировать Unity по email и паролю — те же секреты `UNITY_EMAIL` и `UNITY_PASSWORD`, что и в тестах. Это тот же официальный инструмент GameCI, просто другой способ запуска».

- В Telegram приходит сообщение со ссылкой на игру или с именем упавшей задачи.

### Вопрос 1. Чем webhook отличается от polling?

Polling — ты сам постоянно спрашиваешь сервер: «Есть новое? А сейчас? А сейчас?». Webhook — сервер сам звонит тебе, когда что-то случилось. В CI/CD webhook экономит время и не грузит сервер: после сборки GitHub Actions сразу отправляет POST в Telegram.

### Вопрос 2. Почему токен и `chat_id` нельзя хранить в `main.yml`?

Потому что `main.yml` лежит в репозитории и виден всем. История Git хранит все версии файла, поэтому токен невозможно удалить полностью. Любой, кто увидит токен, сможет писать от имени бота. Секреты GitHub шифруются и маскируются в логах звёздочками.

### Вопрос 3. Зачем `needs` и `if: always()`?

`needs` говорит, от каких задач зависит `notify`, и позволяет читать их результат: `needs.run_tests.result`. `if: always()` говорит: «запускай меня, даже если зависимости упали или пропущены». Без этого при аварии уведомление бы не пришло — а именно тогда оно и нужно.

### Вопрос 4. Какие поля у `sendMessage` и как работает `curl`?

`sendMessage` принимает JSON: `chat_id` — кому, `text` — что. `curl -X POST` отправляет запрос с заголовком `Content-Type: application/json` и телом `-d '{"chat_id":"...","text":"..."}'`. В пайплайне токен и chat_id подставляются из секретов, а текст собирается в зависимости от статуса.

## Общие вопросы, которые могут задать

**Что такое CI/CD?**
CI — непрерывная интеграция: каждый коммит автоматически проверяется тестами и сборкой. CD — непрерывная доставка: готовая сборка автоматически публикуется. В моём проекте CI — это `sanity_check` и `run_tests`, CD — `build_game`, Docker и GitHub Pages.

**Что такое GitHub Actions?**
Это встроенная в GitHub система автоматизации. Ты описываешь пайплайн в YAML-файле `.github/workflows/main.yml`, а GitHub запускает его на своих серверах при событиях: push, pull request или вручную.

**Что такое workflow, job, step?**
Workflow — весь пайплайн. Job — отдельная задача на своём сервере (например, `run_tests`). Step — один шаг внутри задачи: команда `run` или готовый экшен `uses`.

**Что такое секреты?**
Зашифрованные переменные репозитория. В YAML на них ссылаются через `${{ secrets.ИМЯ }}`. Значения не видны в коде и маскируются в логах.

**Что такое артефакт?**
Файлы, которые одна задача передаёт другой через хранилище GitHub Actions. В моём проекте это `WebGL-Build`.

**Что такое GHCR?**
GitHub Container Registry — склад Docker-образов. Образ `platformer-game` лежит там под тегами `latest` и SHA коммита.

**Зачем нужен `fetch-depth: 0`?**
По умолчанию `actions/checkout` качает только последний коммит. Для зеркалирования нужна вся история, иначе `git push` в резервный репозиторий не примет ветку.

**Почему в проекте ветка `main`, а в методичке `master`?**
В проекте с ЛР №1 главная ветка называется `main`. Я заменил `master` на `main` в триггере и в командах, иначе пайплайн не запускался бы.

## Подробнее: CI/CD

**CI (Continuous Integration, непрерывная интеграция)** — это практика, при которой изменения часто вливаются в основную ветку, и каждое изменение автоматически проверяется. Главная цель — найти ошибку как можно раньше, пока она не ушла в релиз.

В моём пайплайне к CI относятся:
- `sanity_check` — быстрая проверка структуры проекта;
- `run_tests` — EditMode- и PlayMode-тесты Unity.

**CD (Continuous Delivery / Continuous Deployment, непрерывная доставка/развёртывание)** — это автоматизация выпуска готового продукта.

- **Continuous Delivery**: сборка автоматически готовится и проверяется, но публикация требует ручного подтверждения.
- **Continuous Deployment**: публикация происходит автоматически, без человека.

В моём проекте после тестов автоматически запускаются `build_game`, `build_docker_image` и `deploy_to_pages` — значит, это ближе к Continuous Deployment: готовая игра сама уходит на GitHub Pages, а образ — в GHCR.

**Как устроен пайплайн в GitHub Actions:**
- **Workflow** — весь сценарий в `.github/workflows/main.yml`.
- **Trigger** — событие запуска: `push` в `main` или `workflow_dispatch` вручную.
- **Job** — отдельная задача на своём виртуальном сервере: `run_tests`, `build_game` и т.д.
- **Step** — шаг внутри задачи: команда `run` или готовый экшен `uses`.
- **Runner** — временная виртуальная машина, на которой выполняется job.

Важно: **каждый job запускается на чистой машине**. Файлы, созданные в одном job, не видны в другом. Именно поэтому между job передают артефакты.

Порядок задаётся через `needs`:
```
sanity_check → run_tests → build_game → build_docker_image
                                   ↘ deploy_to_pages
         mirror_repo (после run_tests)
         notify (always, после всех)
```
Если `run_tests` падает, `build_game` и всё, что от него зависит, не запускается. Это называется **quality gate** — «ворота качества».

## Подробнее: артефакты

**Артефакт** — это файлы, которые job сохраняет в хранилище GitHub Actions, чтобы их могли скачать другие job или человек.

Зачем они нужны:
- job'ы изолированы и не делят файловую систему;
- runner уничтожается после завершения job, вместе с его рабочим каталогом;
- артефакт — это «коробка», в которую кладут результат и передают на следующую станцию.

В моём проекте:
- `run_tests` загружает `test-results` — логи и XML-результаты тестов. Даже если тесты упали, артефакт сохраняется благодаря `if: always()`.
- `build_game` загружает `WebGL-Build` — настоящую WebGL-сборку.
- `build_docker_image` и `deploy_to_pages` скачивают `WebGL-Build` через `download-artifact` и используют его.

Схема:
```
run_tests    --upload--> test-results
build_game   --upload--> WebGL-Build --download--> build_docker_image
                                     --download--> deploy_to_pages
```

**Артефакт ≠ кэш.**
- **Кэш** (`actions/cache`) нужен для ускорения: например, папка `Library` Unity, чтобы не импортировать ассеты заново. Кэш может быть удалён, если устарел или превышен лимит.
- **Артефакт** — это результат, который нужно сохранить или передать. У него есть срок хранения (по умолчанию 90 дней), его можно скачать вручную со страницы run.

**Артефакт ≠ Docker-образ.**
- Артефакт — это набор файлов (обычно zip).
- Docker-образ — это упакованное окружение вместе с приложением, которое хранится в registry (GHCR) и запускается через `docker run`.

**Почему `Builds/WebGL` не коммитят в Git?**
Потому что это результат сборки: большие бинарные файлы, которые меняются при каждом запуске. Их место — в артефакте, а не в истории Git. В Git хранят исходники, а сборку получают заново.

**Почему в ЛР3 были заглушки, а в ЛР5 — настоящая сборка?**
В ЛР3 ещё не было задачи `build_game`, поэтому пайплайн создавал пустые `.gz` через `touch`, чтобы проверить сам механизм Docker. В ЛР5 появился `build_game`, который собирает настоящую игру и кладёт её в артефакт `WebGL-Build`; заглушки больше не нужны.

## GitHub Actions, GHCR, Pages и workflow_dispatch

### `workflow_dispatch` — что это?

Это **ручной запуск** workflow. В файле пайплайна есть блок:

```yaml
on:
  push:
    branches: [ "main" ]
  workflow_dispatch:
```

- `push` — запуск автоматически, когда кто-то отправил коммит в `main`.
- `workflow_dispatch` — в GitHub появляется кнопка **Run workflow** на вкладке Actions (или команда `gh workflow run`). Можно выбрать ветку и запустить пайплайн без нового коммита.

Зачем нужно: перезапустить сборку, проверить ветку без слияния, показать «сломанный» тест на защите. В моей работе я так запускал ветку `LR4-broken`, чтобы показать красный `run_tests` и пропущенные задачи.

### GitHub Actions — что это?

Это встроенная в GitHub **система автоматизации**. Ты описываешь сценарий в YAML-файле `.github/workflows/main.yml`, а GitHub выполняет его на своих временных серверах.

- **Workflow** — весь сценарий.
- **Job** — отдельная задача на своём сервере (`run_tests`, `build_game`).
- **Step** — шаг внутри задачи: команда или готовый экшен.
- **Runner** — временная виртуальная машина, которую GitHub выдаёт на время job'а.

Runner — это не твой компьютер и не постоянный сервер. GitHub создаёт его на время, выполняет job и уничтожает. Поэтому файлы между job'ами передают через артефакты.

### GHCR — что это?

**GitHub Container Registry** — «склад» Docker-образов, встроенный в GitHub. Туда складывают готовые образы, чтобы потом скачать их на любом компьютере или сервере.

Мой образ: `ghcr.io/tiasssd/platformer-game:latest`.

- `ghcr.io` — адрес склада.
- `tiasssd` — владелец.
- `platformer-game` — имя образа.
- `latest` — тег (версия).

Образ лежит в облаке GitHub. Когда ты пишешь `docker run ghcr.io/...`, Docker **скачивает слои образа** к тебе на компьютер и запускает контейнер уже локально. Постоянно работающего «удалённого контейнера» нет: есть образ в хранилище, а контейнер создаётся при запуске.

### GitHub Pages — что это?

Это бесплатный **статический хостинг** GitHub. Он берёт файлы из ветки `gh-pages` (или из артефакта) и раздаёт их по адресу:

`https://tiasssd.github.io/2d_platformer/`

Там нет серверной логики и базы данных — только HTML, JS, WASM и картинки. Для WebGL-игры этого достаточно. Файлы лежат на серверах GitHub, а не на твоём ноутбуке.

### Как всё связано

```
git push
   │
   ▼
GitHub Actions (workflow)
   │
   ├── sanity_check   — проверить структуру
   ├── run_tests      — тесты Unity в контейнере
   ├── build_game     — собрать WebGL в контейнере Unity
   │      └── артефакт WebGL-Build
   ├── build_docker_image — собрать Nginx-образ → GHCR
   ├── deploy_to_pages    — выложить файлы → GitHub Pages
   ├── mirror_repo        — скопировать код в backup-репозиторий
   └── notify             — отправить сообщение в Telegram
```

Аналогия:
- **GitHub Actions** — заводской конвейер.
- **Runner** — временный рабочий стол, который выдают на одну операцию.
- **Job** — станция конвейера.
- **Артефакт** — коробка, в которой деталь едет от станции к станции.
- **GHCR** — склад готовых контейнеров.
- **Docker** — грузовик, который привозит контейнер и запускает его.
- **GitHub Pages** — витрина, где игра доступна пользователям.

## Code coverage и SIGSEGV

**Code coverage (покрытие кода)** — это метрика, которая показывает, сколько строк/веток кода реально выполнилось во время тестов. Если тест прогнал только половину методов, покрытие будет около 50%.

Как это работает: перед запуском тестов в код **вставляются счётчики** (instrumentation) — специальные метки, которые записывают, что вот эта строка выполнилась. После тестов инструмент собирает статистику и строит отчёт.

**SIGSEGV** — это «segmentation fault», ошибка на уровне памяти: программа обратилась по неверному адресу, и операционная система её убила. Код возврата 139 = 128 + 11 (сигнал SIGSEGV номер 11).

В Unity 6 при включённом code coverage в Linux-контейнере инструментирование кода приводит к такому падению. Это **проблема инструмента/окружения**, а не моего кода: сами тесты без coverage проходят нормально. Поэтому в пайплайне стоит `--coverageEnabled=false`: тесты запускаются, но метрика покрытия не собирается.

Зачем coverage вообще нужен: чтобы понимать, какие места игры тесты не проверяют. Для лабораторной это не обязательное требование; важнее, что тесты зелёные и стабильные. Если бы coverage был критичен, пришлось бы менять версию Unity/образ или ждать исправления в Unity 6.
